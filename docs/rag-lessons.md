## 1. 语料与解析

### 1.1 「页码」是谁的页码？物理页 vs 印刷页

- **现象**：评测时发现「引用第 166 页」在源书里根本翻不到，Recall 直接归零，而回答其实是对的。
- **根因**：早期实现先把窗口页抽成一个子 PDF 再走上传链路，结果知识库里存的是子 PDF 的局部页号
  （1..N），而评测锚点用的是源 PDF 的物理页号。两套编号，对不上。
- **解决**：解析源 PDF 后**只筛选、不重编号**（`build_eval_kb.select_pages`），页码与源文档始终一致。
- **教训**：页码是评测与展示的「坐标系」，全链路必须共用同一套。任何「重编号」都会让引用和评测
  同时失效，且极难排查——因为每个环节单独看都是对的。

### 1.2 空页让「段落数 ≠ 最大页号」，末尾正文被漏掉

- **现象**：全库入库后分块数 11111，但 PDF 有 11165 页、非空段落有 11138 页，末尾 27 页正文
  （路山彦决战、尾声、校长）凭空消失。
- **根因**：解析会跳过空页（封面/扉页/无文本页），所以物理页号是**稀疏**的——最大页号 11165
  大于非空段落数 11138。但 `full` 建库窗口用的是「段落数」，把它当成了「最大页号」切窗口，
  导致末尾「页号 > 段落数」的那段正文落在窗口之外。
- **解决**：拆出两个语义——`page_count`（段落数，用于统计）与 `max_page`（最大物理页号，用于切窗口）。
  `resolve_windows('full', ...)` 改用 `max_page`。
- **教训**：**「数量」和「最大编号」不是一回事**。只要有过滤（空页、去重、采样），编号就会稀疏，
  用 `len()` 去推断范围必然出错。凡是按编号切窗口/分片的逻辑，都要用「最大编号」而不是「数量」。

### 1.3 解析结果要落缓存，别和「入库成败」绑在一起

- **现象**：断点续跑时，每次重试都要重新把整本书解析一遍（约 4 分钟），而解析跟入库成败毫无关系。
- **根因**：解析是纯 CPU 的确定性计算，但被放在了「入库」的同一条重试链路里。
- **解决**：解析结果按源文件 sha256 落盘到 `data/cache/parsed-<sha16>.jsonl`（临时文件 + 原子替换）。
  缓存键是文件内容哈希，**换文件必然失效、同文件必然命中**，不会拿到过期文本。
- **教训**：**慢且确定**的步骤要缓存，**快且可能失败**的步骤要重试。两者解耦，重试才不浪费算力。

## 2. 分块

### 2.1 分块策略由「每页平均字符数」决定，不是拍脑袋

- **现象**：早期 `1 分块 = 1 页`，块过碎；改分块参数时没有依据，只能试。
- **根因**：没先量语料的真实粒度。实测《龙族》11138 非空页、235 万字符，**平均每页约 211 字符**——
  远小于 `CHUNK_SIZE=1000`，所以一页天然就是一整块，跨页拼接反而会切断上下文。
- **解决**：先量「每页/每段平均字符数」再定分块参数；`CHUNK_SIZE=1000` / `CHUNK_OVERLAP=200` 下
  分块基本等价于「每页一块」，块元数据带上 `page_start`/`page_end`（闭区间、物理页号）。
- **教训**：分块参数没有「正确答案」，只有「匹配语料的答案」。动手前先统计语料的粒度分布。

## 3. 嵌入模型与部署

### 3.1 云端免费嵌入按「请求数」限流，本地部署才是正道

- **现象**：OpenRouter 免费路由 `liquid/lfm-2.5-embedding-350m:free` 每天 1000 次请求，全库建库
  一次就要 550+ 次，反复调优时根本不够用；且只有 512 token 上下文，长段被截断。
- **根因**：把「按请求数限流」的免费模型用在了「需要大量请求」的全量建库场景上。
- **解决**：本地部署 `Qwen/Qwen3-Embedding-0.6B`（1024 维、32k 上下文、无配额无费用），
  `EMBEDDING_PROVIDER=sentence_transformers`，在 A100 上跑 GPU 推理。
- **教训**：选嵌入后端前先算清「一天要发多少次请求」。全量建库是**一次性批量**，天然不适合
  按请求限流的云端免费额度；本地模型一次性把成本降为零，还顺带解决了上下文截断。

### 3.2 torch 的 CUDA 构建不能比宿主机驱动新

- **现象**：`uv sync --extra local-embed` 装好 torch 后，`torch.cuda.is_available()` 是 `False`，
  且 PyTorch 只在 stderr 打一次 UserWarning，极易被当成「这台机器本来就没 GPU」。
- **根因**：PyPI 默认 torch 已是 cu13x 构建，而机器驱动 535.183.01 只支持到 CUDA 12.2。
  **wheel 内置的 CUDA runtime 新于驱动支持的版本，就会静默失败。**
- **解决**：`pyproject.toml` 加 `[[tool.uv.index]] pytorch-cu124` + `[tool.uv.sources] torch = { index = ... }`
  + pin `torch>=2.6,<2.7`。同时 `_resolve_device()` 在 CUDA 不可用时**退回 CPU 并告警写清华因**，
  而不是抛错（CPU 只是慢，任务还能跑完）。
- **教训**：GPU 环境的版本匹配是「驱动 → CUDA runtime → torch 构建」三层，任何一层不匹配都会
  静默退化成 CPU。装完 torch 先跑一行 `print(torch.cuda.is_available())` 自检，别等跑了一小时才发现。

### 3.3 多卡机器要显式选卡，`nohup` 会吞掉环境变量

- **现象**：共享 A100 机器上，全库重建反复 `CUDA out of memory`，日志显示任务跑在 GPU 0，
  而 GPU 0 已被别的任务占满（只剩 7MiB）。
- **根因**：两个坑叠加——(1) torch 默认落 GPU 0；(2) 写 `CUDA_VISIBLE_DEVICES=3 nohup uv run ...`
  时，那个赋值只作用于 `nohup` 命令本身，**不会传给 nohup 里启动的子进程**。
- **解决**：写成 `nohup env CUDA_VISIBLE_DEVICES=3 uv run ...`，用 `env` 显式把变量传给子进程；
  再用 `torch.cuda.device_count()` 验证选卡生效（可见 GPU 数应为 1）。
- **教训**：后台跑长任务时，环境变量要用 `env` 显式传递，别依赖 shell 前缀赋值；多卡机器先
  `nvidia-smi` 看哪块卡空着再启动。

### 3.4 权重下载要走国内镜像，且要预下载

- **现象**：首次运行本地模型时，从 HuggingFace 下载 1.2GB 权重极慢甚至失败，表现为「建库卡住」。
- **根因**：默认 HF 端点在国内不可达/极慢。
- **解决**：`HF_ENDPOINT=https://hf-mirror.com`；**首次入库前单独试一次模型加载**，别把它和建库
  混在一起——权重下载慢/失败会表现为「建库卡住」，而单独加载能立刻暴露网络问题。
- **教训**：模型加载失败和「入库失败」是两回事，分开验证才能快速定位。

## 4. 向量库与入库链路

### 4.1 全量入库必须能「断点续跑」，否则任何单点失败都要重来

- **现象**：几万个分块 × 分钟级的批量入库，跑到一半网络断/进程被杀，就要从头再来，既浪费又危险。
- **根因**：早期「重跑 = 从头再来」，没有进度概念。
- **解决**：**向量库本身就是进度文件**——契约新增 `stored_chunk_keys(kb_id, doc_id)` 返回已入库的
  `(doc_id, chunk_index)` 集合，续跑时跳过已入库分块。`embed_batches_in_order` 一次性派发全部批次、
  按序 yield、失败时取消未完成的兄弟批次，保证「重跑 = 续跑」，不重算也不累积重复。
- **教训**：**用持久化状态本身当断点**，比单独维护一个进度文件更可靠（不会出现「进度文件说写完了、
  向量库还没写」的错位）。幂等 + 可续跑是批量任务的底线。

### 4.2 zvec 是单写者，写入时不能另开连接读

- **现象**：入库过程中另开一个连接去 `count(kb_id)`，报 `Can't lock read-write collection ... LOCK`。
- **根因**：zvec（嵌入式向量库）单进程单写者，写入期间持有 LOCK。
- **解决**：入库期间的进度探测改用「读日志文件大小/行数」，而不是再开一个 zvec 连接。
- **教训**：嵌入式存储的并发模型和独立服务不同，诊断时要尊重它的锁语义。

## 5. 检索与融合

### 5.1 阈值不是瓶颈，缺的是「词面召回」这一路

- **现象**：小库上 Recall@8 在阈值 0 → 0.30 之间完全不变（75.0%），把阈值降到 0 也一道题都救不回来。
  逐题看，失败题的关键词在语料里**字面就存在**，但稠密召回没把答案页放进 Top-8。
- **根因**：免费 350m embedding + 512 token 截断，稠密召回能力有限；而失败题恰恰是「关键词字面命中」
  的类型，缺一路稀疏检索。
- **解决**：新增 BM25（`k1=1.5`/`b=0.75` + 中文字 bigram 分词）+ 检索组合层 `fuse()`，
  `hybrid` = 向量 ∪ 词面，按 `chunk_key` 去重、取两侧较大分。
- **教训**：**先证明瓶颈在哪，再动手**。用 `--threshold-sweep` 反推整条阈值曲线，一次就把
  「阈值过严」这条假设证伪，避免了在错误方向上浪费一轮迭代。

### 5.2 词面召回会「误命中」摧毁拒答能力

- **现象**：加了词面召回后，拒答正确率 100% → 0%。负样本题「巴黎在哪个国家？」因正文里有一款香槟
  叫「巴黎之花美丽时光」而被命中、注入 context，模型随即放弃拒答。
- **根因**：BM25 归一化后词面第一名恒为权重值，**任何字面重叠都必然过阈值**，误命中不可避免。
- **解决**：加**前置门** `HYBRID_MIN_SPARSE_SCORE`——词面这一路只在「两路里至少一路有实质证据」时启用，
  判据落在 query 级信号上（稠密侧有过阈值候选 或 词面最强匹配 ≥ 门槛）。
- **教训**：召回和拒答是一对矛盾，召回越「宽松」越容易误命中。引入任何一路新召回，都要同时验证
  「负样本是否被误召回」，否则拒答能力会在不知不觉中归零。

### 5.3 全库规模下 embedding 区分度不足，代称化提问会「漂移」到无关页

- **现象**：全库（11,138 分块 / 146 题）实测 Recall@8=79.3%，28 道失败题里 25 道是语料自动生成的
  `fact` 题、3 道是 `alias` 题。逐题看，失败题的检索结果**与期望页差了成百上千页**（如「源稚生背后
  站着谁？」期望 p6007，召回的却是 p7815/p7097/p4280），但召回页的 top1 相似度仍在 0.6~0.73，
  看起来「语义相关」，其实全是无关页。
- **根因**（用本机 Qwen3-Embedding-0.6B 逐题实测锚点页在全库的相似度排名，这是定位的关键一步）：
  语料生成器故意把答案实体换成代词/描述（「谁」「哪个垂死的人」「什么」），**问题与答案页之间
  字面零重合**，只能靠 embedding 的语义关联。但 0.6B 模型对这类含蓄指代区分度不够——

  | 失败题 | 期望页 | 锚点页相似度排名 | 锚点页相似度 |
  | --- | --- | --- | --- |
  | `corpus-p2882-1`（谁用手指了红色星标？） | 2882 | **293 / 11138** | 0.447 |
  | `corpus-p956-1`（校长指向了什么？） | 956 | **693 / 11138** | 0.431 |
  | `corpus-p6007-1`（源稚生背后站着谁？） | 6007 | **919 / 11138** | 0.438 |
  | `corpus-p8905-1`（打量哪个垂死的人？） | 8905 | **72 / 11138** | 0.571 |
  | `sakura-who`（Sakura 是谁？） | 5904 | **12 / 11138** | 0.491 |

  锚点页排名在 72~919 位，远低于 Top-8；top1 分数来自「语义表面相关但实际无关」的页（如 p2882
  这题 top1 是 p4937 的 0.571，比锚点页 0.447 还高）。这是 **embedding 区分度不足 + 题目本身高难**
  的双重结果，不是阈值、也不是融合的问题——把阈值降到 0 也救不回来。
- **解决（方向，尚未合入）**：这类题只有两条路——① **查询改写**：`alias`/`llm` 改写器把「Sakura」
  展开成「路明非」、把「谁用手指了红色星标」改写回「弗罗斯特」等原文措辞（插件点已就绪，默认关闭，
  需在评测集上证明净收益后才开）；② **精排**（`rerank`）：对粗排 Top-8 用更强的判别模型重排。
  两者都遵循「先在小库/全库上证明回归 >2pp 才合入」的门禁。
- **教训**：**「语义相关」和「命中答案页」是两回事**。粗排分数高不等于答得对——失败题的 top1
  分数普遍不低（0.6~0.73），真正要盯的是**锚点页的相似度排名**，而不是召回结果的分数本身。
  定位检索失败，必须下钻到「期望页在全库的相似度排第几」，否则会把「区分度不足」误判成「阈值过严」。

## 6. 生成与拒答

### 6.1 拒绝回答要靠「前置门」，不是靠模型自觉

- **现象**：见 5.2，误命中让模型「看到」了似是而非的上下文，于是放弃拒答。
- **根因**：生成模型倾向于「只要给了上下文就引用」，把「该不该回答」的判断交给了模型。
- **解决**：拒答判断前置到检索层——阈值过滤 + 前置门，检索结果为空/不达门槛时**不注入 context**，
  走「资料中没有」的拒答分支。
- **教训**：拒答能力是 RAG 的「底线」，必须由系统在检索层兜底，不能寄希望于模型在生成层自觉。

## 7. 评测体系

### 7.1 评测必须保证「答案保密」，否则正确率失去意义

- **现象**：早期答题模型能看到参考答案/关键词，跑出来的「正确率」其实是「复读正确率」。
- **根因**：把参考答案和题目一起拼进了答题 prompt。
- **解决**：`generation_input()` 收敛成唯一入口——答题模型**只能看到 question**，参考答案/关键词/禁止词
  都是评测侧判据，只在生成之后使用。在**模型边界**加断言用例（捕获真实 prompt，断言三个 SECRET
  都不在里）钉死这条切分。
- **教训**：评测的「保密」不是口头约定，要落到代码的唯一入口 + 边界断言上，否则一次重构就会泄漏。

### 7.2 评测集要「锚点覆盖全书」，且锚点必须在语料里逐字存在

- **现象**：早期评测集只有 9 条题、锚点集中在少数几页，覆盖不足；且出现过「引用片段不在原文里」的题，
  把「评测集自己写错」误判成「模型答错」。
- **根因**：评测题靠人工挑，覆盖有偏；锚点没有校验。
- **解决**：从语料自动生成评测题（`gen_eval_items.py`，三重硬校验：quote 逐字在原文、关键词在答案里、
  问题与 quote 最长公共片段 ≤5 字），扩到 146 条、锚点覆盖全书 2..11165 页。
- **教训**：评测集的「题」和「锚点」都要能自动校验，否则评测集本身会成为最大的 bug 源。

### 7.3 小库 vs 全库：分清楚「回归」和「主评测」

- **现象**：全量评测集丢给小库（227 页）时，125/135 题的答案根本不在库里，按「召回为空」记 0 分，
  指标读起来像「检索变差」，实际量的是拒答策略。
- **根因**：评测集是照全库出的，小库只覆盖其中 10 条题。
- **解决**：明确**全库 = 主评测场地**，小库退为「快速回归 + 拒答验证」。`run_bench` 加 `--absent-items`
  （默认 skip），按库的真实内容筛掉「引用页不在库中」的题。
- **教训**：评测口径必须和「库的规模」对齐。用错了库，指标就变成了「测拒答」而不是「测检索」。

### 7.4 换嵌入模型 = 换向量空间，之前的基线作废

- **现象**：换成本地 Qwen 后，之前 openrouter 350m 的基线数字无法直接对比。
- **根因**：不同模型的向量空间不同，指标不可跨模型比较。
- **解决**：换模型后重建索引、**重新产出基线**，后续优化在新基线上对比。
- **教训**：任何「换向量」的操作都会让历史指标失效，必须在同一向量空间内做 A/B。

## 8. 工程与运维

### 8.1 `uv sync` 是「精确同步」，不带 extra 会偷偷移除依赖

- **现象**：`uv sync --extra local-embed` 装好 torch 后，过一会儿 `ModuleNotFoundError: No module named 'torch'`。
- **根因**：`uv sync`/`uv run` 只保留被请求的 extra，不带 `--extra local-embed` 的命令会把 torch 当
  多余依赖移除。
- **解决**：所有命令统一带 `--extra local-embed`，或 `uv run --no-sync` 跳过同步。
- **教训**：精确同步工具（uv/poetry）的「安装」和「使用」要成对出现，别混用。

### 8.2 网络假设要实测，别想当然

- **现象**：一直假设「服务器无直连外网」，所有下载走代理隧道，速度只有 1.1MB/s。
- **根因**：没实测就沿用旧假设。
- **解决**：实测发现 `pypi.org`、`files.pythonhosted.org`、`hf-mirror.com` 可直连，但真正的提速是
  **换国内镜像** `UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple`（实测 44.6MB/s）。
- **教训**：网络环境会变，每次长任务前用 `curl` 实测一次源可达性与速率，别依赖记忆里的假设。

### 8.3 macOS 的 `tar` 打包会夹带 AppleDouble 残留

- **现象**：`ruff check` 报 `E902 stream did not contain valid UTF-8`，指向 `._config.py` 这类文件。
- **根因**：macOS 用 `tar` 打包时，会在解包端生成 `._*` 的 AppleDouble 元数据文件。
- **解决**：`find . -name "._*" -delete`；推送多用 `scp` 单文件或注意排除。
- **教训**：跨平台传文件时留意隐藏的元数据残留，`ruff`/`git status` 会立刻暴露它们。

### 8.4 推送多文件别用 basename 猜目标路径

- **现象**：推送时 `README.md` 被覆盖到了 `benchmark/README.md`；根目录散落 `config.py`、`evaluation.md`
  等历史推送失误的残留副本。
- **根因**：`for f in ...; cp $(basename $f) $f` 这种写法在「不同目录同名文件」时必然出错。
- **解决**：用「文件 → 目标路径」的显式映射，或 tar 打包后按目录结构解包。
- **教训**：批量推送要显式声明目标路径，别依赖文件名唯一。

### 8.5 `pkill -f` 会误杀执行它的 shell

- **现象**：`pkill -f "uv sync"` 把执行这条命令的 shell 自己也杀了（命令行含该字符串）。
- **根因**：`pkill -f` 匹配整个命令行，当前 shell 的命令行里恰好含被匹配的字符串。
- **解决**：用 `pkill -f "[u]v sync"`（正则自匹配技巧，`[u]` 匹配 `u` 但不匹配字面 `[u]v sync`）。
- **教训**：`pkill`/`pgrep` 用正则时，把首字符写成字符类可以避免匹配到自身。

## 附：这套流程沉淀出的通用方法论

1. **先量后改**：改任何参数前，先统计语料/数据的事实（每页字符数、请求次数、阈值曲线），用数据证伪假设。
2. **分离关注点**：慢且确定的（解析、权重下载）缓存/预下载；快且易失败的（入库、调用）重试/续跑。
3. **用状态本身当进度**：断点续跑用向量库已入库的内容，不另维护进度文件。
4. **评测保密落到代码**：答案保密靠唯一入口 + 边界断言，不靠口头约定。
5. **换向量空间 = 重测基线**：任何换模型/换分块/换索引的操作，指标都要在同一空间内重新对比。
6. **每次改动留痕**：`CHANGELOG.md` 记「为什么做、怎么做、效果如何」，可复述、可回溯。
